코딩 에이전트는 컨텍스트 예산의 대부분을 코드 검색에 사용한다. 기존 문자열 검색(grep)은 설정이 필요 없고 즉시 실행되지만 노이즈가 많으며 정의와 호출, 주석을 구분하지 못한다. 반면 언어 서버 프로토콜(LSP)을 통한 의미 기반 검색은 정밀하고 타입 정보를 제공하지만, 인덱싱된 서버가 구동 중이어야 하며 심볼 하나당 왕복 통신 비용이 발생한다. 저자들은 의미 기반 검색이 토큰 효율성이 더 높다는 주장은 거의 모든 곳에서 언급되지만 실제 측정은 거의 이루어지지 않았다고 지적하며, 동일한 작업 성공률에서 LSP와 문자열 검색 간 토큰 차이를 분리하는 공개된 자료가 부재함을 문제제기한다.

이 논문은 '성공까지의 토큰 수'라는 단일 지표를 통해 질문을 공식화하고, 의미 기반 검색을 다른 변수로부터 분리하는 5단계 제거 실험(ablation)을 설계했다. 또한 세 가지 사전 정의된 실패 모드를 측정 가능한 변수로 매핑하고, 파이썬과 타입스크립트 저장소를 대상으로 Claude 및 Sonnet 등 주요 모델들의 예비 연구 결과를 보고한다. 저자들의 주장에 따르면 LSP 사용의 토큰 효율성은 조건부이며 일반적으로 부정적이다. 심볼 이름 기반 위치 파악 작업에서는 LSP가 토큰을 더 소모(+6%~+118%)하며, 에이전트가 선택할 수 있는 경우 이를 무시하는 경향을 보인다.

참조 완전성(reference-completeness) 측면에서 LSP는 정밀도를 높이지만 토큰 절감 효과는 없으며, 에이전트의 철저함에 의해 결정되는 재현율(recall) 한계를 넘지 못한다. 토큰 절감 효과는 가장 약한 모델에서만 관찰된다. 도구 선택은 작업 유형에 따라 달라지며, 모델들은 위치 파악 작업에서는 문자열 검색을 기본으로 사용(의미 기반 검색 사용률 0~6%)하지만 참조 작업에서는 프롬프트 없이도 약 절반의 경우 LSP를 선택한다.

실제 테스트 실행으로 점수화된 수정 작업에서 두 방식의 격차는 가장 뚜렷하다. 문자열 검색은 다중 파일 이름 변경을 완벽하게 해결하는 반면, 위치 정보만 제공하는 LSP는 호출 지점을 놓쳐 4분의 3이 실패한다. 인덱스가 완성되고 텍스트가 보강된 완전한 LSP도 이 격차를 대부분 좁히지만 완전히 해소하지 못하는데, 이는 이름 변경 작업이 의미 기반 참조에서 제외되는 주석과 문자열까지 수정해야 하기 때문이다. 저자들은 따라서 LSP를 무조건적으로 사용하는 것이 아니라 작업 클래스, 모델 능력, 문자열 노이즈에 따라 적응형 라우팅을 적용해야 함을 시사한다.
