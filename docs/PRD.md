# PRD: 초록

## 목표

영문 AI 원문을 **여섯 갈래로 좁혀** 한글 요약으로 정리해 공개하는 1인 운영 사이트.

사이트 이름은 **초록**(논문의 abstract). 원문을 그대로 옮기는 번역이 아니라 **추려 적는 것**이 이 사이트가 하는 일이다 — 이름·문구·출처 표기가 전부 그 사실에 맞아야 한다.

다루는 범위는 넓어졌지만 하는 일은 같다. 하루에 쏟아지는 논문·릴리즈·커뮤니티 논쟁은 수백 건이고 이 자리에 남는 것은 몇 건뿐이다 — **무엇을 뺐는지가 이 사이트가 하는 일의 절반이다.** 다만 남의 글을 옮기기만 하지 않는다. 직접 재 보고 직접 만들어 본 기록도 싣는다. 그런 글에는 옮길 원문이 없으므로 대신 **측정 조건과 실패한 시도**를 적는다.

## 사용자

- **독자** (외부 공개): AI 기술 동향을 한글로 빠르게 훑고 싶은 개발자·연구자. 로그인 없이 열람, GitHub 계정으로 댓글.
- **운영자** (1명): 글을 작성·발행·수정한다. GitHub OAuth 로그인.

## 분류 축 셋

셋을 섞지 마라. 각각 답하는 질문이 다르다.

| 축 | 질문 | 필드 | URL | 부호 |
|---|---|---|---|---|
| **주제** (1급) | 무엇에 대한 글인가 | `axis` — 필수·단일 | `/topics/{axis}` | 번호(mono) |
| **소스** | 원문이 어디서 왔는가 | `category` — 필수 | `/{category}/{slug}` | 안료 3색 |
| **포맷** | 글이 어떤 꼴인가 | `format` — 선택 | 없음 (`?format=`) | 없음 |

태그(`tags`)는 **고유명사 전용**이다 — 모델·툴·기법 이름. 축·포맷을 태그로 표현하지 마라.

### 주제 축 (6개, 닫힌 집합)

`/topics` 가 매체의 지도 노릇을 하려면 **6축 편수 합이 전체와 같아야 한다.** 그래서 `axis` 는 필수·단일이다. 두 축에 걸치는 글에서 하나를 못 고르는 것은 편집 회피다 — 부차 주제는 태그가 받는다.

| # | slug | 이름 | 짧은 이름 |
|---|---|---|---|
| 01 | `retrieval` | 검색·RAG | 검색 |
| 02 | `serving` | 서빙·학습 | 서빙 |
| 03 | `voice` | 음성 | 음성 |
| 04 | `agent` | 에이전트·자동화 | 에이전트 |
| 05 | `domain` | 도메인·정책 | 도메인 |
| 06 | `vibe-coding` | 바이브코딩 | 코딩 |

**축에 색을 주지 마라.** 안료 3색은 카테고리 전용이고 네 번째 안료는 사실상 없다. 축의 부호는 번호다.

### 발행 포맷 (5개, 선택)

| slug | 이름 | 구성 |
|---|---|---|
| `explainer` | 기술 해설 | 무엇 / 기존과 차이 / 우리 스택 적용 가능성 |
| `digest` | 주간 다이제스트 | 이번 주 논쟁 — 무슨 일 / 왜 시끄러운가 / 양측 주장 / 내 판단 |
| `replication` | 재현 검증 | 커뮤니티 성능 주장을 직접 실측. 하드웨어·설정·측정 방법 필수 |
| `kr-first` | 국내 첫 해설 | 영어권에서만 논의된 이슈를 한국어 실무 맥락으로 |
| `fieldnote` | 실전 기록 | 직접 만들어 본 기록 |

`replication`·`fieldnote` 는 `notes` 카테고리다 — 옮길 원문이 없는 글이다.

## 카테고리 (소스 축, 3개 고정)

설정 파일(`src/lib/categories.ts`)로 데이터화한다.

**slug 은 고정이다.** 이미 발행된 글 주소·RSS·sitemap 이 걸려 있으므로 바꾸지 마라. 화면 표기만 바꿀 수 있다.
**개수도 늘리지 마라** — 안료 팔레트와 `Record<CategoryAccent,…>` 5곳이 딸려 온다.

| slug | 이름 | 짧은 이름 (목록용) | 성격 |
|---|---|---|---|
| `hf-blog` | 릴리즈·발표 | 소식 | 모델·라이브러리 릴리즈, 기업 연구 블로그, 툴 문서 변경 |
| `papers` | 논문 | 논문 | arXiv·OpenReview 논문 리뷰. 수식·도표 비중 높음 |
| `notes` | 관측·기록 | 관측 | 커뮤니티에서 관측한 것과 **직접 해 본 것** |

밀집 목록의 구분 열에는 짧은 이름을, 카테고리 페이지 제목에는 긴 이름을 쓴다.

> `hf-blog` 라는 주소는 허깅페이스 블로그만 옮기던 시절의 흔적이다. 이미 걸린 링크를 끊지 않으려고 **주소는 그대로 두고 이름만 바꿨다.** 감추지 말고 소개 페이지에 적어 둘 것.

## 핵심 기능

**공개**
1. 홈 — 마스트헤드 + 최신 글 목록. **첫 화면에서 글이 보여야 한다** (히어로가 화면을 차지하지 않는다)
2. 카테고리별 목록 (페이지네이션·태그 필터)
3. 글 상세 — TOC, 출처·라이선스 표기, 읽기 시간, 이전/다음
4. 본문 표현 — 수식(KaTeX) · 차트(Recharts) · 다이어그램(Mermaid) · 고급 표 · 이미지(캡션·확대)
5. 검색(클라이언트), RSS, sitemap, OG 이미지
6. 댓글(Giscus), 조회수
7. **태그 색인** — 태그별 글 수와 태그별 목록
8. **아카이브** — 연·월별 발행 목록
9. **소개** — 운영 원칙, 번역이 아니라 요약이라는 점, 출처·인용 정책, 오류 제보 경로

**관리자** (`/admin`, 로그인 필수)
10. 글 목록 대시보드 (발행/초안, 조회수)
11. MDX 에디터 + 실시간 프리뷰
12. GitHub 커밋으로 발행 → Vercel 자동 재배포
13. 이미지 업로드 — 글과 같은 방식(GitHub 커밋)으로 같은 레포의 `public/uploads/` 에 저장 (ADR-005). 외부 스토리지를 쓰지 않는다. 글 저장과 원자적으로 한 커밋일 필요는 없다.

## MVP 제외 사항

- **자동 수집·LLM 요약 — 이 레포에서 빠졌다.** 별도 private 레포 `chorok-collect` 가 담당하고,
  산출물을 `bot/*` 브랜치 PR 로만 올린다. 이 레포에 수집기·크롤러·LLM 호출을 만들지 마라
- 다중 저자 / 권한 등급
- 뉴스레터·이메일 발송
- 다국어 (한글 전용)

> **광고·유료화는 제외 목록에서 뺐다.** Vercel Pro 라 약관상 제약이 없다. 다만 지금 범위도 아니다 —
> 도입하려면 별도 결정과 phase 가 필요하다. **요청 없이 광고 스크립트나 결제를 넣지 마라.**

## 디자인

- 읽기 우선. 콘텐츠가 주인공이고 UI는 물러난다.
- **개인 블로그가 아니라 연구 피드처럼 보여야 한다.** 목록은 조밀한 표, 본문은 넉넉한 단폭.
- 라이트/다크 양쪽 지원 (장문 독해용).
- 중성 무채 베이스 + **카테고리 3색**(정보 부호로만 사용). **보라/인디고 금지.**
- 본문은 세리프, UI는 산세리프, 데이터·코드는 모노. **한글에도 웹폰트를 지정한다** — 안 그러면 OS마다 다르게 보이고 한 문장 안에서 서체가 갈린다.
- **균일한 반복을 피한다.** 모든 구역이 같은 구조·같은 여백이면 만들다 만 템플릿처럼 보인다.
- 상세는 `docs/UI_GUIDE.md`.
